# Entregable 6 — Modelo de IA

**Regla de oro:** la IA **sugiere**, nunca **decide**.

---

## ⏱️ En 30 segundos

- La IA lee el **ticket + el código de Git**, clasifica el **frente de trabajo** (correctivo / evolutivo / nuevo desarrollo / innovación) y propone **complejidad, calidad, impacto y riesgo**. La sugerencia de **complejidad/peso aparece en FitDesk**, donde el validador la confirma.
- Entrega una **sugerencia con explicación** ("por qué creo que es complejidad 4").
- **Tú apruebas o ajustas.** Tu decisión, no la de la IA, es la que cuenta.
- Todo queda registrado → defendible y auditable.

---

## 1. Qué analiza la IA

| Fuente (disponible hoy) | Qué extrae |
|-------------------------|------------|
| **Ticket** | Descripción, tipo, prioridad, módulo, historial de reaperturas |
| **Git (commits/diff/PR)** | Archivos y módulos tocados, líneas, tablas/APIs afectadas, tests añadidos, code review |

De ahí estima señales: cantidad de archivos, módulos afectados, tablas, APIs, reglas, pruebas, indicios de deuda técnica.

---

## 2. Qué sugiere (las 4 salidas)

| Salida | Escala | En qué se basa |
|--------|--------|----------------|
| **Frente de trabajo** | correctivo/evolutivo/nuevo/innovación | Tipo de ticket/tarea + naturaleza del diff de Git |
| **Complejidad** | 1–5 | Alcance del cambio (archivos, módulos, BD/APIs) |
| **Calidad** | 0–100 | Tests, code review, validaciones añadidas, estilo |
| **Impacto** | 0–100 | Nº de módulos/usuarios afectados, criticidad |
| **Riesgo** | bajo/medio/alto | Cambios sensibles, sin tests, módulos frágiles |

Cada salida viene con una **explicación legible** y la **evidencia** que la respalda.

---

## 3. Cómo decide (pipeline)

```
1. Ingesta     → toma ticket + diff de Git
2. Extracción  → calcula señales objetivas (#archivos, #módulos, tests…)
3. Análisis    → modelo de lenguaje interpreta + reglas heurísticas
4. Sugerencia  → 4 salidas + explicación + evidencia
5. Validación  → llega a tu bandeja; apruebas/ajustas
6. Registro    → se guarda sugerencia, tu decisión y el delta
```

> **Híbrido reglas + LLM:** las señales objetivas (contar archivos, tests) son reglas deterministas; la interpretación ("esto huele a causa raíz") la aporta el LLM. Así es **explicable y difícil de manipular**.

---

## 4. Cómo se evita que la IA se equivoque o la engañen

| Riesgo | Mitigación |
|--------|------------|
| Descripción inflada del dev | La IA pesa **más el código real (Git)** que el texto |
| IA sesgada/opaca | Toda sugerencia es **explicable** + revisada por ti |
| Alucinación | Las cifras duras vienen de reglas, no del LLM |
| Manipulación (fragmentar tickets) | Detección de duplicados/patrones + auditoría |
| Deriva con el tiempo | **Recalibración trimestral** comparando IA vs tus decisiones |

---

## 5. Qué modelo usar (recomendación técnica)

- **MVP:** un LLM de proveedor vía API (p. ej. familia Claude) para el análisis de lenguaje, + reglas propias para las métricas de Git. Rápido de montar, sin entrenar nada.
- **Más adelante:** afinar con el **histórico propio** (tus decisiones de validación) para que la IA se parezca cada vez más a tu criterio.
- **Privacidad:** si el código es sensible, evaluar despliegue privado/redacción de secretos antes de enviar diffs al modelo.

---

## 6. Lo que la IA NUNCA hace

- ❌ Fijar la nota final.
- ❌ Acreditar puntos o liberar bonos.
- ❌ Decidir promociones.
- ✅ Solo **sugerir y explicar**.
